# Smart Proxy Route Helper v0.4.0 Plan

Last updated: 2026-08-17

## Release theme

**Explainable Proxy Troubleshooting**

The goal of `v0.4.0` is to make Smart Proxy Route Helper substantially better at answering two questions without DevTools:

1. **Why is this site or action not working through the proxy?**
2. **What is the smallest safe routing change that is likely to fix it?**

`v0.4.0` should remain focused on diagnosis, explanation, explicit user control, and safe recovery rather than expanding into a general-purpose multi-profile proxy manager.

## Release commitment

### Core scope — required for v0.4.0

The release is considered meaningful and shippable only when all three core areas below are implemented and hardened.

#### 1. Route Health

Create one consolidated current-site/device health view, primarily in the Popup.

It should distinguish at least:

- local proxy configuration present or missing;
- proxy reachability state: not checked, reachable, unreachable, timed out, or authentication-related failure where Chrome exposes enough information;
- Chrome proxy `levelOfControl` state;
- PAC applied or not applied;
- extension enabled or disabled on the current device;
- current hostname effective route: Proxy, explicit Direct, or unconfigured default Direct;
- exact or parent rule responsible for the current route;
- diagnostic override active or inactive;
- latest applicable diagnostic result and timestamp;
- whether the current site has unresolved related-domain candidates worth reviewing.

Product requirement:

> The user should be able to identify the main failure class from the extension UI without opening Options or DevTools.

The UI must distinguish configured intent from verified browser/runtime state and must not imply that traffic was successfully proxied when reachability or browser control is unknown.

#### 2. Dependency Rescue

Upgrade Related Domains / Recorder from a mostly flat hostname candidate list into ranked, explained recommendations.

Candidate confidence groups:

- **Likely required**
- **Possibly required**
- **Probably third-party or optional**

Evidence may include:

- request/resource failure;
- hostname first appearing after a specific recorded user action;
- repeated appearance during that action;
- source signal such as fetch, XHR, beacon, resource load, or resource error;
- registrable-domain or known site relationship;
- bundled site-scoped hint;
- analytics/advertising/noise classification;
- existing Proxy/Direct coverage;
- conflict with an explicit child rule.

Each recommendation should explain why it is shown in user-facing language, for example:

- appeared after file upload started;
- resource load failed;
- known asset host for this site;
- already covered by a parent Proxy rule;
- conflicts with an explicit Direct rule.

Recommendations must be sorted by decision value rather than alphabetically.

Rule creation remains explicit. Discovery, ranking, or confidence must never silently create or widen a route rule.

Required representative fixtures/smoke scenarios:

- ChatGPT file upload;
- YouTube preview/image dependency case;
- Letterboxd or another clear image/asset-host case.

#### 3. Undo and local snapshots

Make consequential routing changes recoverable.

Create a device-local snapshot before operations such as:

- settings import;
- multi-domain additions;
- mixed route batches;
- rule scope expansion;
- redundant-rule cleanup;
- other operations that replace or modify multiple route rules.

After a successful operation, show a concise summary such as:

> Added 4 rules, changed 1

and provide an immediate **Undo** action where practical.

Requirements:

- keep a small bounded list of recent snapshots;
- snapshots stay in local storage and are not synced;
- validate snapshot format before restore;
- do not include credentials, raw request URLs, or unsanitized request data;
- restore should avoid duplicate rules and preserve stable rule identity where possible;
- every multi-rule operation in the supported set should be recoverable in one explicit action.

## Stretch scope — desirable, but not release-blocking

These remain `P1`. They should ship in `v0.4.0` only if the three core areas are complete, stable, and the additional work does not meaningfully delay the release.

If either item starts expanding the schedule or permission/privacy surface, defer it to the next release rather than weakening the core.

### First-run proxy check

Provide a guided setup/check flow that clearly explains:

- the extension does not provide a VPN or proxy server;
- the user must already have a compatible proxy endpoint;
- domain rules and local proxy settings have different sync behavior.

Desired flow:

1. Enter scheme, host, and port.
2. Validate locally.
3. Check endpoint reachability.
4. Explain common outcomes such as connection refused, timeout, authentication required, invalid configuration, or browser control blocked.
5. Create or test the first route.

A public-IP comparison is not required for `v0.4.0` and should not be added if it weakens the local-first/no-backend posture.

### Sanitized diagnostic report

Add an explicit **Copy diagnostic report** action for support/GitHub issues.

The report may include safe state such as:

- extension version;
- browser/OS information available through safe APIs;
- sanitized proxy configuration representation;
- extension enabled state;
- Chrome proxy control state;
- PAC application state;
- effective route and matched rule scope;
- latest diagnostic outcome;
- candidate counts/confidence groups;
- known visibility limitations.

It must not include raw URLs, paths, query strings, fragments, credentials, cookies, headers, request/response bodies, browsing history, or unreviewed captured host lists.

## Research only — not a release commitment

### Early DIRECT requests / startup behavior

Investigate requests that may occur before the extension runtime is fully ready, including pinned tabs, service workers, startup navigation, and browser-level activity.

Research questions:

- which cases can actually be detected;
- which can safely be made fail-closed;
- which are outside extension visibility/control;
- whether Chrome lifecycle behavior introduces reproducible regressions;
- how the UI should communicate unavoidable limitations.

Do not ship a broad startup-blocking mechanism in `v0.4.0` unless behavior is reliable, testable, recoverable, and explainable.

## Delivery order

### Phase 1 — specification

- define Route Health state model and precedence;
- define candidate evidence model, ranking, and confidence groups;
- define snapshot schema, retention, and restore semantics;
- review Chrome permission and Web Store implications before implementation.

### Phase 2 — Route Health

- implement pure state-resolution logic and tests;
- expose proxy control/PAC/current-rule explanations;
- integrate the consolidated health view into the Popup without weakening current quick actions.

### Phase 3 — Dependency Rescue

- normalize recording evidence into structured candidate records;
- implement ranking and explanations as pure tested logic where possible;
- add representative fixtures and smoke scenarios;
- preserve explicit selection, conflict preview, and confirmation.

### Phase 4 — recovery

- implement bounded local snapshots;
- add post-action summaries and Undo;
- cover imports, batch additions, scope expansion, and cleanup operations.

### Phase 5 — optional P1 work

Only after the core is stable:

- first-run proxy check;
- sanitized diagnostic report.

Either may be deferred without blocking `v0.4.0`.

### Phase 6 — hardening and release

- regression tests for routing, diagnostics, import/export, language switching, duplicate prevention, mixed batches, PAC restoration, and snapshots;
- manual smoke on representative partially broken-site scenarios;
- permission/privacy/release-surface audit;
- update Store screenshots/text where the user-visible flow changed materially;
- replace version-specific Store wording such as **“New in version 0.3.0”** with a more durable heading such as **“Recent updates”** during the next Store metadata update.

## Release definition of done

`v0.4.0` is ready to publish when:

- Route Health, Dependency Rescue, and Undo/snapshots are complete;
- representative ChatGPT/YouTube/asset-host scenarios pass manual smoke;
- no discovery path creates or widens rules without explicit confirmation;
- consequential multi-rule changes in scope can be undone;
- configured intent and actual Chrome/proxy state are clearly distinguished;
- existing routing precedence and fail-closed semantics remain intact;
- required permissions remain minimal and any permission change has an explicit product/review decision;
- privacy claims, README, release docs, screenshots, and Chrome Web Store listing match the shipped behavior;
- automated tests, typecheck, build, packaging, audit threshold, deterministic package, and release-surface checks pass.

The first-run proxy check and sanitized diagnostic report are **not required** for this definition of done unless they are already complete and stable by release time.

## Explicit non-goals for v0.4.0

- Full SwitchyOmega/FoxyProxy profile compatibility.
- Multiple proxy-profile architecture as a core release requirement.
- Arbitrary regex URL routing rules.
- Remote rule subscriptions or remotely controlled classification logic.
- Automatic rule creation or automatic broadening without confirmation.
- Default-on diagnostics or passive browsing-history collection.
- Required `<all_urls>` or broad host permissions.
- `webRequest`, `webNavigation`, `chrome.debugger`, or persistent content scripts unless a separate explicit product decision changes the permission strategy.
- Telemetry, analytics, ads, backend services, or developer access to user rules.
- Built-in VPN/proxy service.

## Product guardrails

Preserve the current principles:

1. **Explain before expanding.** Better diagnosis is more valuable than more configuration types.
2. **Exact before broad.** Default to the narrowest safe route and preview broader coverage.
3. **Explicit before automatic.** Discovery may be assisted; route creation remains user-controlled.
4. **Recoverable before powerful.** Consequential changes need preview, summary, and rollback.
5. **Local before remote.** Keep settings, classification, diagnostics, and snapshots local unless a future explicit decision changes the privacy model.
6. **Actual state before configured intent.** UI wording must distinguish what is configured from what Chrome actually controls and what has been verified.

## Relationship to the product roadmap

`docs/product-roadmap.md` remains the product-level source of truth. This release-specific plan clarifies the shipping boundary for `v0.4.0`:

- the roadmap's three `P0` areas are the committed release core;
- the roadmap's `P1` onboarding and diagnostic-report items are stretch scope;
- the early-request investigation remains research only unless it produces a clearly safe, testable design.
